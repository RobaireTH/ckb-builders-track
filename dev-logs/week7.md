## Key Learnings
- RGB++ achieves isomorphic binding: a Bitcoin UTXO maps one-to-one to a CKB cell, so ownership lives on Bitcoin while state and computation live on CKB. This is the cleanest explanation I have read of why CKB's cell model is structurally compatible with Bitcoin — they are both UTXO-descended, just at different levels of expressiveness. RGB++ exploits that symmetry deliberately.
- The single-use seal primitive from RGB++ clicked for me in the context of ckb-pop. In RGB++, a Bitcoin UTXO is a seal: once spent, the asset moves and the old state is irrevocably closed. ckb-pop badges work on the same logic — the badge cell is permanently bound to the attendee's lock script. It is not transferable, not reusable. You can think of the attendance event itself as the seal: it was opened (QR window), consumed (attendee scanned and signed), and the badge is the closed proof. I had not framed it that way before.
- RGB++ uses OP_RETURN on Bitcoin to commit a hash of the corresponding CKB transaction. ckb-pop's event-anchor cell does something structurally similar: it commits `SHA256(name || date || location || description)` into cell data on CKB, anchoring off-chain metadata to an immutable on-chain record. Both are commitment schemes. The difference is RGB++ bridges two chains; ckb-pop bridges the physical world and the chain.
- Reading the transaction structure RFC while writing the transaction builder in Rust was the right order to do it. The fee is implicit — the difference between input capacity and output capacity — which means if you miscalculate you either pay too much or the node rejects the transaction silently. There is no explicit fee field. That is intentional but it caught me off guard.
- DOB0 is the render specification for Digital Objects — it defines how clients should interpret the metadata hash in a badge cell and render a visual representation. ckb-pop badges currently store a raw content hash; DOB0 gave me a clearer picture of where that design could go if badges needed to be visually renderable in wallets that support the standard.

## Brief
- This week I built `ckb-pop-cli`, the terminal companion to the protocol. The goal was to let event organisers run the full flow — create events, open attendance windows, and monitor QR rotation — without needing a browser open. Most of the week was transaction plumbing: sourcing live cells, calculating capacity, wiring cell deps, serialising the right way for the CKB node.
- Reading the RGB++ light paper while doing this was genuinely clarifying. I have been thinking of ckb-pop badges as "soulbound tokens" — a term borrowed from Ethereum — but that framing does not really fit CKB's model. RGB++ gave me a better vocabulary: ckb-pop badges are single-use seal closures. The event is a seal. The attendee's signature over the HMAC QR is the spending proof. The badge cell is the committed output. That framing is native to how UTXO chains actually think about ownership and it makes the protocol easier to explain to someone already familiar with Bitcoin or CKB.
- The other thing RGB++ made concrete is the difference between ckb-pop anchoring and RGB++ anchoring. RGB++ puts a commitment on Bitcoin and backs it with CKB computation. ckb-pop puts a commitment on CKB and backs it with a real-world event. The chain is always the settlement layer; what changes is what you are settling. I think there is an interesting design space where ckb-pop events could eventually be anchored via RGB++, letting a Bitcoin UTXO vouch for the event creation and a CKB cell carry the badge state. Not building that now, but the architecture would support it.

## Practical Progress
- Built the full `ckb-pop-cli` in Rust from scratch: CLI argument parsing, config management at `~/.ckb-pop/config.toml`, contract address registry for testnet, crypto module (HMAC-SHA256 QR codes, SHA256 type-script args, window secrets), and an async RPC client wrapping both the CKB node and the indexer.
- Implemented the **browser signer**. Since private keys live in browser wallets and not on disk, the CLI spawns a tiny localhost HTTP server, opens the signing page in the user's default browser, and collects the wallet's signed response via a POST back to localhost. The CCC SDK bundle is embedded in the binary at compile time so the signing page has no CDN dependency.
- Wrote a camelCase-to-snake_case translation layer between Rust's serialisation and CCC's JavaScript expectations. CKB's JSON API is entirely snake_case; CCC expects camelCase on its transaction input. The mismatch caused silent signature failures that took a while to diagnose — the transaction was being accepted for signing but the resulting signature was invalid because the fields were hashed in the wrong form.
- Bumped the fee rate to 2000 shannons per kiloweight and enforced minimum cell capacity on all outputs. Both of these were required for the node to accept transactions; without them, the node rejected them with errors that did not point at the actual problem.
- Added integration tests for the RPC client against Pudge testnet and an end-to-end test that walks the full proof-of-presence flow: create event → open window → derive QR HMAC → attend → mint badge → verify anchor cell on-chain.
- Diagnosed and fixed a UX gap: events created through the CLI were not appearing on ckb-pop.xyz because the site filters My Events by exact `creator_address` string match, and the CLI can be signed into a different wallet than the browser. The fix was two-pronged: the CLI now prints the creator address upfront with a clear tip to connect the same wallet on the site, and the site now has an "Add CLI Event by ID" input in the gallery so you can paste the event ID printed by the CLI and track it regardless of which wallet address created it.
- The CLI now also waits for the anchor transaction to confirm on-chain (polling every 15 seconds, up to 90 seconds) and then calls the backend's `/activate` endpoint automatically to record the TX hash. Previously this had to be done manually with a curl command after the fact.

## Challenges
- The browser signer works but the architecture is fragile in ways I have not fully stress-tested. The CLI opens a browser tab and waits for a POST back to localhost. If the browser tab takes too long to load, or the user closes it, or the port is already in use, the CLI hangs or fails with a confusing error. I need a proper timeout and a cleaner failure message. This is the most likely thing to break for a new user.
- The camelCase/snake_case bug cost me more time than it should have because neither side tells you when you have passed the wrong format. CCC accepted the transaction, signed it, and returned a result — but the signature did not verify because the field names were different. I would love to know if there is a canonical way to bridge Rust and CCC that other builders have settled on, or if everyone is rolling their own translation layer.
- Fee rate and minimum cell capacity are still somewhat empirical. I settled on 2000 shannons/KW after 1000 was rejected, but I do not have a principled formula for a given transaction size. The SDK does not abstract this and I could not find a clear recommendation in the docs. Is there a standard testnet floor I should target?
- The "Add CLI Event by ID" feature on the website is a workaround for a real identity problem: the CLI wallet and the browser wallet are separate identities. The correct fix is probably for the website to look up events by on-chain type-script args (which encode the creator lock script directly) rather than by the backend's stored address string. That would make CLI events and browser events indistinguishable. It is on my list but it requires changing how the frontend queries the chain.
- Still testnet-only. The mainnet code path used to `panic!`; it now returns a graceful error. But there is real work remaining before mainnet is viable — accurate fee estimation, deployment costs for the contracts, and testing against a chain where mistakes are expensive. I am leaving this until the protocol is fully stable on Pudge.
