## Key Learnings
- **The Nervos YouTube playlist worked best consumed in sequence, not cherry-picked.** I went into the week expecting to watch the trilemma / Layer 2s explainer and stop. What I actually did was work through the channel end-to-end, and the value compounded — earlier episodes set up vocabulary (cell, type script, capability model, Nervos DAO) that later episodes lean on without re-introducing. The trilemma video was the anchor and is what I am citing in the readings list, but the framing that stuck — L1 as a settlement-and-ownership layer, L2 as where throughput lives, with Fiber / rollups / channels all *anchored to* L1 rather than competing with it — only made sense to me once I had heard it stated three different ways across the playlist. Cherry-picking would have left me with a slogan; the playlist left me with a mental model.
- **"Web5" is a positioning argument I had been quietly skipping past, and reading it alongside this week's audit work made it click.** The Nervos framing is that Web3 settled for token ownership — you own the asset, but the application state and the rules around it still live on someone else's L1. Web5 (their term, not mine) is the claim that with the cell model, *every* piece of state can be a first-class user-owned object, not just balances: profiles, sessions, app data, social graph, all of it sit in cells with user-controlled locks. The piece I had not internalized: this is only meaningful if the L1 itself stays simple enough that users can actually verify their state independently, which is exactly why CKB resists the temptation to bake application logic into the base layer. Reading this in the same week as fixing `ckb-academy`'s playground 404 was a small irony — even a Web5 stack needs working docs and a live playground for anyone to build on it.
- **Bitcoin and CKB share more of a security model than I had been giving CKB credit for.** The "Bitcoin and CKB Security Models" piece walks through what is actually shared: both are PoW with Nakamoto consensus, both use UTXO-style accounting (CKB's cells are a generalization of UTXOs, not a replacement), both treat the script as a pure verifier that says yes or no to a state transition rather than mutating shared state. The divergence is on *what a cell can hold and how scripts can read context*: CKB cells carry arbitrary data and a type script, scripts can inspect the full transaction (not just their own input), and the VM is RISC-V instead of Bitcoin Script. The practical upshot for builders: every security argument that applies to Bitcoin's UTXO model — replay resistance, deterministic validation, no global mutable state — carries over to CKB, and the cell model is the *extension* surface, not a re-foundation. This reframes how I want to write `pckt`'s threat model: start with the Bitcoin-style baseline (what can the chain itself guarantee?) and only then describe what the type script adds.
- **The trilemma framing in the YouTube piece is more useful as an architectural commitment than as a slogan.** The standard "decentralization, security, scalability — pick two" reading is well-worn; what the Layer 2s video does well is make the L1/L2 split a *contract* rather than a fallback. CKB L1 commits to decentralization and security and explicitly does not chase TPS at the base layer. Scalability is then a property the L2 ecosystem provides — Lightning-style channels, Fiber, rollups, side-chain-like constructions — all anchored to CKB's L1 for settlement. The thing I want to keep in mind for `pckt`: the packet-lock contract belongs on L1 because it is fundamentally about ownership and claim verification (security-shaped problems), but the share-link rendering, claim-link delivery, and packet-discovery feed are L2-shaped problems and do not need to be on-chain. I had been sloppily mixing those tiers in the early `pckt` design; this is the clearest articulation I have read of where the line goes.
- **The Week 19 SSRI lessons reshape the `pckt` claim flow, not the contract.** With no shipping pressure this week, the right shape became obvious: `pckt`'s packet-lock does not need a UDT-style trait surface. It needs exactly two methods — `Packet.preview(packet_outpoint)` returning sender label/amount range/lucky-slot config, and `Packet.claim(packet_outpoint, recipient_lock) -> Transaction` returning an incomplete tx for CCC to fill. Everything else stays verifier-side. And because Week 19's `ssri-server` reading showed the WASM-in-browser path is closed, the share-link page will call a hosted runner over JSON-RPC. That is one new endpoint, not a rearchitecture.

### Secondary — audit lessons from the dead-link work
- **Dead-link rot is the cheapest signal of how trustworthy a doc site is, and the easiest to miss without tooling.** Reading the docs page-by-page, I would have caught maybe two of the seven `docs.nervos.org` issues — the ones I happened to click. `lychee` against `website/docs/` surfaced everything in one pass: 12 missing internal paths, 4 hash mismatches, 3 dead external hosts. Any docs site worth maintaining needs a link-check in CI.
- **Most "broken external links" are actually broken *internal* links pretending to be external.** The majority of `docs.nervos.org` failures were authors writing absolute URLs like `https://docs.nervos.org/tech-explanation/...` instead of relative paths, which then silently broke when sections were reorganized. The fix is not just patching them; it is moving them to relative paths so the next reorganization does not re-create the same class of bug.
- **A dead host is a different kind of bug from a dead path.** `Wyminer` and `brc-20.io` are real NXDOMAIN dead domains. The right move is removal (or canonical-successor repoint), not silent retargeting. Treating "the host disappeared" the same as "the path moved" is how docs end up pointing at parked domains.
- **`ckb-academy`'s rot was course-specific and bundle-cached.** The dead links in the NFT-getting-started chapters lived in both the `.mdx` source *and* the rendered JS bundles (`chapter_*-*.js`). A docs/courseware site has two surfaces and both need verification — fixing source without re-checking bundles leaves learners with the old broken URLs.
- **The Playground REPO_PATH 404 is a product decision, not a typo.** `site/src/components/Playground/ProjectEditor.data.ts:8` hardcodes a GitHub repo that is now 404, with no working successor. The text-link fixes I shipped are safe; the playground source is left as a maintainer call, deliberately not silently changed.

## Reflections — `pckt` and the SSRI integration shape
A week off `pckt` shipping was the right call. The thing I would have built without Week 19's research was a thicker, more UDT-shaped contract surface, because that is the only SSRI example I had read in detail before. The reflection now is that `pckt`'s claim flow is fundamentally a tx-assembly problem, not an asset-metadata problem, and the SSRI method I actually need is the `transfer(...) -> Result<Transaction, _>` *shape* — incomplete transaction returned to the dApp for CCC to fill in inputs and `cellDeps` — not the trait it lives on. Picking the smallest possible surface (`Packet.preview` for the share-link page, `Packet.claim` for the claim button) keeps the contract auditable and means a future wallet wanting to integrate `pckt` natively only has to learn two method paths.

The other reflection is that the WASM-in-browser constraint from Week 19 is not a problem to route around — it is an architectural decision I would have made wrong without the research. The share-link page already calls a backend for the packet preview render; routing the SSRI call through that same backend (or a sibling `ssri-server` instance) is one more endpoint, not a structural change. I would have spent days trying to get a CKB-VM WASM build working in the share-link bundle if I had not read the `ssri-server` README footnote.
